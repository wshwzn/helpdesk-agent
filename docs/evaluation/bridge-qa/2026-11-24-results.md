# 充值后关联问答对照结果

20条自建用例、50份虚构企业资料，同题比较单次检索与受控补查。默认文本模型 `deepseek-flash`，两组同一模型和生成核验流程；候选25、相似度下限0、Top5，参数及题集沿用充值前冻结版本。

## 结果

| 指标 | 单次检索 | 受控补查 |
| --- | ---: | ---: |
| 必要事实完整回答 | 10/20（50%） | 20/20（100%） |
| 完整关联证据 | 10/20 | 20/20 |
| 两文档关联题完整回答 | 10/10 | 10/10 |
| 三文档关联题完整回答 | 0/10 | 10/10 |
| 平均检索次数 | 1.0 | 2.2 |
| 平均规划模型调用次数 | 0 | 1.55 |
| 正常交付（含追问、证据不足） | 19/20 | 20/20 |

“完整回答”要求交付ANSWERABLE、两项必要字段及数值单位正确、引用目标细则且关联链证据齐备。不是以“模型自己说通过”或“HTTP成功”判分。自动规则检查后，开发助手阅读全部返回结论、数值单位与引文进行核对；尚非独立人工标注的标准评测。

两组首轮真实检索结果完全相同，逐题比较已验证。40次运行全部保留，未调整提示或参数重跑挑选成绩，未将充值前402失败混入本轮效果。运行前后文档、知识库与模型配置一致。全部交付引文均在对应证据原文中存在。

## 收益与代价

三文档题的初检缺少业务组到规则的映射，单次组中7题追问、2题保留证据不足、1题复核失败。补查组沿初检已有业务组编码自行生成查询，补齐映射后全部正确交付两项标准。

例如 `b02` 云杉交付：档案给出业务组M2239；补查获得M2239绑定差旅方案K1056，结合细则回答住宿上限680元/晚、报销提交期限17个自然日。查询由生产规划器生成，没有注入标准补查词。

补查组共44次逻辑检索，单次组20次，平均每题增加1.2次检索；另有31次规划模型调用，不能把“额外1.2次检索”描述为全部成本。由于首轮被两组物理共享，本轮实际HTTP检索总数为44，而不是两组逻辑次数相加的64。

9题无需补查，10题共执行3次检索，1题执行5次检索。`b07`两文档题初检已经足够，仍额外查询2次检查规则，未改善答案；`b20`三文档题执行5次检索后完成。保留这些冗余成本，不宣称每次补查都有收益。

## 使用边界

这是围绕关联查找构造的20题专项回归，资料短、字段固定、没有真实制度的复杂条件和冲突，容易取得高分。结果证明本次关系补查机制起效，不代表任意知识库准确率100%，也不证明已解决上一轮公开制度评测的复核误拒问题。

本轮只有一遍真实模型运行，不代表多次运行的稳定通过率。首轮已有目标规则但缺绑定映射的题目较多，收益主要是补齐关系，而非每题都从零检索目标事实。交付前元数据核对使用冻结快照；不覆盖在线会话、上下文、SSE或并发性能。

## 简历建议

推荐保留样本范围与整数计数，避免孤立的100%：

> **受控多跳检索：** 根据证据缺口生成补查计划，结合查询去重与预算控制；在20条自建跨文档关联用例中，将完整回答数由10条提升至20条，平均额外检索1.2次。

面试解释：固定50份资料和同一次初检，对比补查开关；成功要求两项事实、单位、引用和关联链均匹配标准。全部提升来自10条三文档关联问题，不将小规模合成场景推广为生产准确率。
