# 企业跨文档关联问答对照

目标：为“受控多跳检索”提供一个小规模、可解释的实验，比较单次检索与受控补查的必要事实回答完整性及检索开销。不是公开标准数据集，也不是实际用户准确率。

## 固定场景

`cases.json` 包含50份虚构企业资料、20道问题：10道关联两份文档，10道关联三份文档。覆盖差旅、运维、采购、权限、培训五种业务，每题询问两个明确的数值标准。

- 两文档：实体档案 → 规则编码 → 两项执行标准。
- 三文档：实体档案 → 业务组编码 → 规则编码 → 两项执行标准。
- 其他实体的相似规则作为干扰资料。编码按固定随机种子分配，不能按序号推导对应关系。
- 每份资料一个chunk，共50个chunk；全部ALL通用、同一有效期、已发布，不混入版本资格实验。
- 题集、映射、标准值和参数在首次模型实验前固定。资料由开发助手构造，属于针对关联查找能力的合成场景，不能称为真实业务日志。

## 对照方法

使用单路候选25、向量相似度下限0、每次最终返回5个chunk。两组共享同一次真实首轮检索；单次组关闭 `KnowledgeMultihopProperties.enabled`，补查组启用。模型、生成、引用校验、语义复核与修订流程相同。

生产 `KnowledgeEvidenceCollector` 负责生成查询并执行补查，最多三轮、五次检索，调度预算90秒；默认 `taskPlanningEnabled=false`。不向规划模型传标准答案、目标规则编码或预设补查词。

检索通过本地管理员接口实际执行向量化、ES双路召回及资料准入；CLI复用生产问答服务，只有默认库绑定和交付前元数据核对替换为实验快照。运行前后检查知识库、文档、模型配置未变化。实验不覆盖HTTP聊天、SSE、上下文改写，也不是并发压测。两个离线线程执行，各题交替组别顺序，避免全部先跑某一组。

## 评分

- 完整证据：累计召回包含全部必要关联文档。每文档一个chunk，因此本场景可按文档判断关联链覆盖。
- 必要事实完整交付：实际交付 `ANSWERABLE`，两项字段及数值单位在结论中明确对应，引用目标规则，且完整关联链在证据中。运行失败或部分回答不算通过。
- 自动规则不能判断所有语义错误或同义表述，输出逐题核对表供核对原文、引用与额外结论。不能将规则通过率描述成独立人工准确率。
- 统计每题检索和规划调用数；首轮在对照中物理共享，组内计作一次逻辑检索。额外成本以补查组减去单次组计。耗时不用于端到端性能声明。
- 不删除不利题目，不为提高成绩反复调低Top-K或增加与实际无关的干扰材料。若调整规则或题集，应保存新版本并说明。

## 使用

管理员令牌只放在忽略目录 `data/public-campus/tokens.json`，已有脚本可通过正常登录生成。需要本地后端、MySQL、ES、OSS及可用的默认模型。

```powershell
python scripts/evaluate_bridge_qa.py prepare
python scripts/evaluate_bridge_qa.py run --output data/bridge-qa/available-model-run
python scripts/evaluate_bridge_qa.py summarize --output data/bridge-qa/available-model-run
python -m unittest discover -s scripts -p test_evaluate_bridge_qa.py
```

`prepare` 创建专用知识库并上传、索引、发布，不改变默认库。`run` 编译测试目录CLI并调用真实模型，输出目录必须不存在。新增最小模型预检，遇到余额不足则停止正式运行，预检不计入问答成绩。`summarize` 完全离线，生成报告及逐题答案核对表。
