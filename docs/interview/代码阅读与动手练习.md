# 代码阅读与动手练习

目标是能解释一次请求和一次资料更新，而不是背全部类名。所有实验使用独立知识库；默认库全局共享，结束后恢复。真实问答、检索和索引会产生模型调用，切勿把失败重跑当作原先通过。

## 建议阅读顺序

路径均相对仓库根目录，Java 主包为 `src/main/java/com/anying/helpdesk/`。

| 顺序 | 重点文件 | 读完应能回答 |
| --- | --- | --- |
| 1 | `conversation/dto/SendMessageRequest.java`、`conversation/service/ConversationServiceImpl.java`、`ConversationPersistenceService.java` | 请求如何归一化？为何模型调用不放在长事务？SSE 何时发送正文？ |
| 2 | `knowledge/answer/TrustedKnowledgeAnswerService.java`、`KnowledgeApplicabilityService.java` | 何时先澄清？续答恢复什么？技术错误与业务不足怎么区分？ |
| 3 | `knowledge/service/KnowledgeDocumentEligibilityService.java`、`KnowledgeRetrievalService.java` | ALL 与多个地区怎么过滤？为何 MySQL 是资格权威？RRF 在哪合并？ |
| 4 | `knowledge/answer/KnowledgeEvidenceCollector.java`、`KnowledgeRetrievalPlan.java`、`KnowledgeMultihopProperties.java` | 哪些搜索消耗共享预算？何时停止？现在真正启用哪个规划协议？ |
| 5 | `knowledge/answer/KnowledgeCitationCatalog.java`、`KnowledgeAnswerGuard.java`、`KnowledgeAnswerModelClient.java`、`answer/trace/` | 原文怎么取得？复核能保证什么？失败用量如何保留？ |

随后读同名或同模块测试，而不是立即改提示词。`src/test/java` 中检索 `lease`、`claim`、`superseded`、`cancel`、`clarification`，用测试的前置条件理解业务分支。

## 四个学习实验

### 实验一：亲手跟踪新旧制度交接

阅读 `scripts/verify_knowledge_delivery.py` 和[交付回归](../evaluation/runs/2026-10-21-项目交付回归.md)。纸上先写下四个时刻的预期：只有上传、索引完成未发布、候选未审核、候选审核完成。对照真实报告中的文档 ID、发布状态、检索集合和答案证据。

不需要再次调用模型，也可以从归档 JSON 解释为什么同一问题先答 640、候选上传后仍应答 640、审核后才答 760。最后解释为什么撤回新版不自动恢复旧版。

### 实验二：解释迟到 worker

画出 A 领取任务 → A 超过租约 → B 领取 → B 写 ES 并激活 → A 迟到写 ES 的时间线。阅读任务条件更新和 ES 批次命名，指出哪一个 SQL 条件阻止 A 切换有效指针。回答“有租约后为什么仍需要批次隔离”。

使用已有本地测试复核；不必在真实数据库修改 lease。注意测试多使用 H2，不能把模拟租约结果说成已经完成真实双实例宕机演练。

### 实验三：复盘一条没有交付的回答

打开[多范围真实回归](../evaluation/runs/2026-10-21-多范围联合检索验证.md)和对应数据，定位上海/广州题。按“召回是否正确 → 草案是否表达部分可答 → 引用是否有效 → REVIEW 为什么拒绝”逐层解释。

不要用“模型不够聪明”结束分析。指出结构检查、语义审核各自覆盖什么；再说明为什么一次新运行通过，也不能抹掉先前误拒。

### 实验四：解释联合检索与多跳

先用已有诊断比较“上海与北京上限”和“某计划对应等级，再查等级上限”。前者可联合过滤后一次召回；后者下一条查询可能依赖已找到的中间关系。逐项数 `retrievalRun.searches` 与 PLANNING/DRAFT/REVIEW 阶段，不把两路 ES 召回、一次逻辑搜索和一次文本模型调用混为一谈。

最后解释五次搜索上限如何让系统停止，以及预算耗尽并不能保证证据完整。当前 N02 漏冲突仍是限制，见[候选取舍](../evaluation/runs/2026-10-21-单列表规划候选取舍.md)。

## 自检标准

- 不看笔记，用自己的话讲完“一份文档如何变成可用知识”。
- 能指出至少两个真实的事务边界，说明网络调用为何放在外面。
- 能从一条诊断分清召回不足、草案错误、协议失败和审核误拒。
- 能讲清两个已实现机制及其各自一个限制。
- 能明确回答当前没有原生 Tool Calling/MCP，并提出保留现有约束的扩展方案。

达到这些标准后再把相应内容放进简历。下一阶段以使用、阅读和口述练习为主，不再因为面试关键词继续堆功能。
