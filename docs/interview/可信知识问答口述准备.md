# 可信知识问答：口头面试准备

这份材料按“不展示源码、不展示页面”的交流方式组织，阶段 44 更新。先用自己的话讲清业务问题和关键选择，再按追问展开。资料是虚构制度，测试在本地进行；项目不是已经上线的企业生产系统。当前状态统一见[交付清单](../项目交付清单.md)，简历选句见[简历描述与能力边界](简历描述与能力边界.md)。

## 一分钟介绍

> 我做的是一个企业制度知识问答项目，用 Spring Boot、Spring AI、MySQL 和 Elasticsearch。它不只是把文档检索出来交给模型回答，我重点处理了三个问题：资料会过期或被撤回，不同地区的规则可能不同，模型即使引用了真实原文也可能解释错误。
>
> 查询前先按发布状态、有效期和用户明确选择的范围过滤资料，再做 BM25 和向量混合检索。模型生成结构化答案并选择证据段落，由后端提取完整原文，再单独调用模型复核语义。答案分成可回答、需澄清、证据不足和冲突四种状态。
>
> 对缺地区的问题，我增加了可配置的主题判断和多选澄清续答；复杂问题可以在固定预算内补查。资料更新通过持久索引任务、候选新版和审核交接完成，外部 OSS 来源变化也复用这条流程。另外我做了固定回归和运行诊断，能分清错误发生在检索、引用还是复核。我也遇到过复核误杀，所以会固定失败输入对比方案，而不是仅凭几次聊天效果决定改动。

不要一次讲完所有类名。对方更可能沿着“为什么这么设计、如何保证、怎么验证”追问。

## 三分钟展开：一次问答如何走完

1. 所有新请求进入同一可信服务，由后端强制执行检索及核验步骤。旧客户端传AGENT只作为输入别名，规范为KNOWLEDGE后执行；历史AGENT回答仍保留原标记，不能补称为已核验。
2. 用户未指定范围时，ALL 只查通用资料。若知识库配置的某业务主题需要地区，分类模型只选主题 ID，服务端返回地区选项；通用流程类问题不必一律追问地区。
3. 资料筛选以 MySQL 为权威，检查 READY、PUBLISHED、有效期和适用范围，再给 BM25/KNN 提供允许的文档 ID。ALL 不是所有地区的并集。
4. BM25 处理关键词匹配，向量检索补充语义匹配。两路分数不可直接相加，当前使用 RRF 按排名融合，单路贡献为 `1/(60+rank)`；这里没有另外训练排序模型。多个范围先联合初检，缺地区和证据缺口再有限补查；整题共享三轮、五次逻辑搜索、两次规划上限，最终只生成、复核一次。
5. 模型输出状态、结论和证据段落编号。后端从本轮目录提取原文，校验编号和引用结构，再进行一次独立语义复核。
6. 交付前复查文档准入。正文、用量和核验报告一同保存；SSE 也是核验完成后才发完整正文，不提前把未经核验的草案流给用户。
7. 管理员可以用运行 ID 查看各阶段的输入快照、结果、耗时和用量。普通客户不会看到被否决的草案。

## 可以重点讲的四个设计

### 1. 有效知识不是“上传时间最新的文件”

例如上海住宿规则有旧版 500 元、当前版 600 元和未来版 700 元。不能按上传时间选最后一份，因为未来版本现在还不能用；也不能只在提示词里要求模型判断日期。元数据先确定哪些文档当前可用，正文再用于回答。

MySQL 管理业务版本、范围、发布状态和半开有效期；ES 保存分块及检索所需副本。查询前和返回阶段都有资格检查，生成结束后还会复查。这里是多个阶段的校验，不能声称 MySQL 与 ES 或模型生成全过程具有强原子一致性。

若两个有效文档的适用条件重叠但结论矛盾，保留双方依据并返回 CONFLICT。不同地区的 600 元和 450 元本身不构成冲突。当前只检查召回结果中的冲突，没有全库扫描。

### 2. 引用可信与结论正确是两个问题

早期让模型直接复制 quote，会出现空格等原文复制错误。现在让模型选择本轮证据段落，后端提取原文。目录每轮有独立标识，可以拒绝跨轮、跨来源或不存在的段落编号。

这证明的是“引用确实来自这份原文”，不是“结论一定由原文推出”。真实引文写 600 元，模型结论仍可能写成 900 元，也可能漏掉“不予报销”。因此还需要语义复核；复核依然可能误判，不能当事实正确性的证明。

### 3. 澄清续答是一段受约束的业务流程

“住宿上限是多少”缺地区，但“报销多久内提交”可能不缺地区。管理员为主题配置业务描述和可选范围，分类模型只识别主题，是否需要追问由服务端按配置决定。主题识别仍有模型不确定性，并非百分之百可靠的意图分类。

澄清报告保存原问题、知识库、配置修订和可选范围。客户续答带澄清消息 ID 和显式范围；服务端验证会话归属、来源是否为最新可续答消息、选项和配置修订，再恢复原问题。不能把“我选择上海”当成新的检索问题。

当前最多支持三个明确范围，可多选原卡片中的地区。配置名称的明显匹配可以免去追问，但不是完整自然语言填槽或长期记忆。新问题不自动继承旧地区，补充后仍可能没有有效资料。配置被修改或旧卡片已经被消费，需要重新提问。

### 4. 可追溯的失败比“只展示成功回答”更有用

运行诊断按阶段保存召回、段落选择、草案、复核结果和错误码。调用失败、协议失败、引用无效和复核否决都属于技术失败，不能统一算作正确拒答。

诊断以独立短事务尽力保存，写入失败不会让本来可完成的回答失败；代价是诊断可能缺失或停留在 RUNNING。回答完成不等于诊断必定完整，没有做到两者的分布式原子提交。

## 常见追问及回答要点

| 追问 | 可以怎么回答 |
| --- | --- |
| 为什么不只加一句“不要编造”？ | 提示无法阻止无效资料进入候选，也不能保证引用真实。资格过滤和引用解析交给程序，语义判断才交给模型。 |
| 为什么还用 AI 复核 AI？ | 第二次调用独立检查全部候选和草案，可以发现一些误读；但使用同一配置模型存在相关错误，也会误杀。我把它视为一道可能失败的检查，不宣称是独立事实来源。 |
| 为什么拒绝得越多不一定越好？ | 正确回答被拒绝也影响可用性。要分别看正例误杀、负例错误放行和技术失败；全报错的系统不能拿到漂亮的“安全分”。 |
| 怎么知道是检索差还是生成差？ | 先看诊断候选是否覆盖问题，再看段落选择和解析，最后看草案与复核。复核专项固定问题、证据和草案，避免每轮重新生成造成输入变化。 |
| 为什么选 MySQL + ES？ | 业务元数据、版本及状态更新适合事务数据库；ES 提供关键词和向量检索。需要处理副本滞后，不能拿索引里的旧状态直接当最终权威。 |
| 两次同时发送消息会怎样？ | 会话已有生成中消息时拒绝新生成；准备消息时沿用会话版本乐观锁，冲突事务回滚。模型调用在短事务之外执行，避免长时间持有数据库事务。 |
| 用户取消 SSE 后模型才返回怎么办？ | 取消与最终落库共用结束状态检查，迟到结果不能覆盖已经取消的状态。不能据此保证厂商停止计费。 |
| 范围过滤等于权限隔离吗？ | 不等于。当前范围是制度适用条件，客户不能查看管理员诊断，但没有实现按员工部门等复杂文档 ACL。系统也不是多租户。 |
| 换个账号能用另一个知识库吗？ | 当前默认库是全局的；账号只隔离自己的会话。练习库与评测库分开，但评测临时切换全局默认库时不能同时进行其他练习。 |
| 为什么没有换框架或增加多 Agent？ | 当前难点是证据、条件、状态和评测。沿用 Spring AI 能实现这些约束，迁移框架本身不能解决复核误杀或知识过期。 |
| 现在的不足是什么？ | 同模型复核有误杀和漏检，题集小且不是独立人工金标准；只检查召回冲突，已存在漏冲突案例。增量同步限登记 OSS 来源、文档级与单向，孤儿清理和上传中断恢复有限。 |
| 为什么不是上传后立刻索引并发布？ | 首次上传只保存待处理文件，元数据完整后显式提交任务，索引完成仍是草稿。技术上可检索与业务上允许作为依据是两件事。 |
| worker 重复执行会污染索引吗？ | 每次领取有独立令牌和 ES 批次，只有有效租约持有者能激活索引指针。仍可能重复向量化及留下不可见批次，不是 exactly-once。 |
| 如何保证新版审核前不影响旧版？ | 新候选独立存储与索引，审核事务确定交接边界。检索按当前有效时间筛选，未审核的 DRAFT 不参与；撤回已生效新版不会自动复活旧版。 |
| 为什么还要变更识别，上传时不是已知变化了吗？ | 内部接口直接提交，外部登记目录才需要扫描识别变化。它不是后台自动处理全部 PENDING 文件。 |
| 没有 Tool Calling 怎么解释？ | 当前模型产出结构化检索计划，后端有界执行，属于带规划的 RAG 工作流。没有原生 Tool Calling/MCP；未来可以把只读检索封装为工具，但保留资格、预算和最终核验。 |

## 如何谈实际测试结果

以下历史评测保留各自模型与题集，不能混合计算当前准确率。当前 E 轮在“dp官方”上执行一次固定交付回归：11 项生命周期断言通过，六个问答场景五个通过、一个技术失败；澄清初问另计一次，共七次消息请求。失败在 REVIEW，草案含正确地区金额和差额但未交付。详见[交付回归报告](../evaluation/runs/2026-10-21-项目交付回归.md)。

多跳候选的历史 12 题曾有 10 通过、1 未通过、1 技术失败，但 N02 漏冲突，未满足采用门槛，因此候选保持关闭。当前仍用原有有界规划与 BASELINE 复核。当前 E 轮没有重新验证 N02，不宣称它已修复。

- 阶段 30 的真实端到端运行共 18 次问答，16 次自动检查通过、2 次复核否决。原固定 15 题为 13/15。应说“这轮开发回归结果”，不要说“系统准确率达到 88.9%”。自动检查包含状态、关键点和引用，不能替代全部语义审阅。
- 两个地区的澄清续答均通过，上海和北京分别得到 600 元和 450 元；这说明两条业务路径跑通，不能推导所有问题的澄清准确率。
- 曾比较逐项检查表与原布尔复核。96 次固定草案调用中，检查表没有减少错误放行，增加误杀、一次协议失败和约 50.9% 的已知 Token，因此保留了原策略。这是有依据的取舍，不需要把每次实验都说成提升。
- 本轮增加真实 B03/B09 正反样本后，28 题 × 两种策略 × 两轮，共 112 次复核。上下文候选总误杀从 6 次降为 4 次，但第一轮错误放行增加、挑战样本退化，Token 增加约 28.8%，因此仍未采用。
- 原 B03 草案这次连基线也批准了，原 B09 草案则两种策略两轮都否决。这个例子可以说明：历史失败不一定稳定重现，某个总指标改善也不等于目标问题已经解决。具体数据见 `../evaluation/runs/2026-10-19-真实失败复核与练习环境.md`。
- 可以陈述实际集成和单元测试覆盖了越权、旧消息、配置变化、撤回、取消和引用伪造；测试数量本身不是系统质量证明。

## 不展示代码时，如何证明自己理解了实现

准备三个可以现场讲清的例子，每个只需两分钟：

1. **资料撤回**：为什么用户补充了上海，系统仍然回答证据不足？讲当前有效文档、通用流程与地区标准的区别，而不是简单归咎于模型。
2. **真实引文的错误结论**：引用写 600 元，结论写 900 元。讲清结构/出处校验能保证什么、语义复核再检查什么，以及复核误判如何进入诊断。
3. **被否决的优化方案**：为什么检查项更多却没有采用？讲冻结输入、正反例、成本和采用门槛，承认开发题集的局限。

如果被问到个人贡献，按实际情况说明哪些设计、调试和验证是自己理解并参与的。可以说“开发过程中使用 AI 辅助编码，我重点梳理了业务约束、验证链路和失败案例”；不熟悉的部分不要描述成独立完成且完全掌握。建议拿一条真实诊断，自己不看笔记解释其每个阶段。

## 练习顺序

先用一分钟介绍说明项目，再让对方从上表任选一个问题追问。回答按“遇到的问题 → 做法 → 为什么 → 如何验证 → 尚存限制”组织，每次最多选择一个具体例子。

稳定练习环境的准备与使用见 `../demo/trusted-knowledge/练习环境.md`。它供自己确认行为，不要求面试时打开页面或展示源码。
