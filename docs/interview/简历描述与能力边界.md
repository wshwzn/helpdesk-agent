# 简历描述与能力边界

项目可命名为“企业知识问答与文档版本管理系统”。按实际投入及理解程度选择两到三条，不必把下列内容全部塞进一份简历。以下均为本地学习项目，不暗示真实企业上线或独立完成全部代码。

## 后端开发侧重

- 基于 Spring Boot、MySQL、OSS 与 Elasticsearch 构建企业知识问答后端，拆分文档处理与发布状态，实现候选新版、重复识别、审核交接和按有效时间过滤。
- 设计数据库持久化索引任务，通过有限重试、租约及执行批次隔离处理重复执行和迟到写入；先写 ES 隔离批次，再在事务中切换有效索引指针。
- 接入登记目录的 OSS 单向增量同步，按对象指纹识别变化，将新增与更新复用索引和审核流程；外部文件缺失仅标记待核查，避免自动撤回有效制度。

面试重点：为什么上传不直接发布、为什么需要两个版本号、为什么租约之外还需要执行令牌、为什么不能只更新 ES 中的状态字段。

## Agent / RAG 应用侧重

- 实现企业知识问答工作流，以 BM25/KNN 和 RRF 融合检索，结合发布状态、有效期及适用范围筛选证据，支持最多三个范围的联合比较与澄清续答。
- 实现有界多跳检索，模型根据已有证据规划补查，后端统一执行去重、准入及预算控制；整题共享最多三轮、五次搜索和两次规划，并保留逐轮诊断。
- 将回答拆为结构化结论、引用及业务状态，由后端解析引用原文，再进行语义复核与交付前资格检查；通过固定题集记录检索缺口、错误答案、技术失败及模型用量。

面试重点：多跳为什么不同于一次把问题拆成三份、规划与工具调用有什么区别、引用真实为什么不代表结论正确、为什么最终没有采用某个得分更高的候选。

## 一分钟介绍

> 我做的是一个企业制度知识问答项目，用 Spring Boot、MySQL、OSS 和 Elasticsearch。重点是资料持续变化时，回答还能依据当前有效版本。内部文件提交后通过持久任务索引，新版先成为候选，管理员审核后才接替旧版；外部 OSS 来源的变化也复用这条流程。
>
> 问答时先按发布、时间和地区筛选，再做关键词与向量混合检索。复杂问题可以在预算内根据已找到的证据补查；多地区比较先联合检索，缺条件则澄清。最后由后端提取引用原文，模型做语义复核，交付前再次检查资料资格。
>
> 我还保存固定回归和逐阶段诊断。实际测试暴露过漏冲突和复核误拒，所以不会把有引用当作一定正确，也没有为了增加功能数量强行接 Tool Calling 或 MCP。

不要背熟自己不能解释的机制。开发使用了 AI 辅助，可以据实说明：“AI 协助编码，我通过设计讨论、阅读实现和固定回归理解并验证关键链路。”尚未自己读懂的部分先读代码，再决定是否写入简历。

## 为什么没有工具调用，以及怎样扩展

可以回答：“这个项目当前动作集中在证据检索和核验，我选了固定工作流，把检索范围、调用次数和交付条件交给服务端控制。模型仍然参与下一步查询的选择，但没有使用厂商原生工具调用协议。它是一种 RAG 应用设计选择，不能说已经实现了 Tool Calling。”

若以后需要更灵活的动作，可把检索、读取指定来源上下文封成只读工具，给出严格参数模式；原有准入、预算、去重、引用目录和最终审核继续保留。鉴权从会话上下文获取，不能接受模型自报身份。检索结果是不可信外部数据，不能把其中指令当系统命令。工具错误需可诊断，重试有上限。

MCP 是可以进一步考虑的工具连接方式；仅把函数写成工具并不等于接入 MCP。只有明确需要对接外部工具服务或复用标准连接时再选它。若增加写操作，还需要权限、幂等和适当的用户确认。这些都是**未来方案，当前未实现**。
