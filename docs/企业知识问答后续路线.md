## 项目定位与完成边界

面向单个企业内部的知识助手：知识维护者管理资料及版本，员工查询制度和操作流程；助手根据证据回答，必要时澄清条件或补充检索。主线为“资料持续更新 → 按需检索证据 → 核验后回答”。

客服工单退出产品主线。Agent 能力体现为根据已有证据决定下一步检索，而不是保留创建、查询工单工具。技术上继续复用 Spring AI、现有后端和可信问答链路。用户的面试主要是口头交流，页面展示不是交付门槛。

本次确定的必做范围止于：定位收敛、文档级增量更新、受控多跳检索、统一可信问答入口，以及相应评测与口述材料。不因发现一个新失败就自动扩大功能范围。

## B 阶段拆分：增量更新

1. **内部文档提交与可靠索引（B1）**：上传后先配置元数据，使用“保存并提交”一次请求完成元数据保存与任务入库；后台自动执行，管理员仍单独发布。保留仅保存和手动索引接口，不扫描所有 PENDING 文档。持久任务支持有限重试、租约恢复和执行批次隔离；任务领取扫描不是来源变更识别。
2. **上传新版与审核替代（B2）**：针对已有文档上传新版，明确新旧关系并比较文件内容及业务元数据；变化文档整体重新解析、分块和向量化，复用 B1。原始文件和候选版本独立保存，失败不影响旧可用版本。准备成功后由管理员审核切换；未来生效资料不能提前撤回旧资料。
3. **来源接入与定时变更识别（B3）**：以明确配置的 OSS 外部来源为优先方向，不再默认本地目录。区分知识库托管文件和外部来源，逐份明确维护入口；仅扫描纳入同步管理的来源。首次发现、修改、未变、缺失各有规则。完整扫描才能判定缺失，撤回策略显式约定，不将外部删除自动等同于业务失效。沿用 B1/B2 的任务、候选和发布机制。

内部上传或上传新版经过本系统接口，变更已知，直接创建任务，无需再扫描 OSS 才发现。外部来源才需要轮询或事件通知来发现变化；内容变化与索引是否完成是两个维度。单纯上传和仅保存元数据的待处理文档不被定时调度擅自接管。当前不做双向回写或两边同时编辑同一份资料。

区分三个概念：来源内容发生变化、业务制度版本变化、技术索引构建批次。不能把它们都塞进一个“版本号”，也不能按文件修改时间决定制度生效。未来生效资料不得导致旧资料提前撤回。

第一版采用文档级增量，不做段落级 Embedding 复用或全库索引切换。字段、表结构、锁与恢复协议在每个实现步骤开始前给出具体设计；此前讨论的表名和流程只是设计方向。涉及数据库时新增 Flyway 迁移并同步数据库字典。

## A/D 阶段的兼容原则

- 退出客服工具先从注册和提示词做起，旧模块和数据不立即删除；任何破坏性清理另列具体迁移方案。
- 主问答使用可信服务；旧AGENT输入在阶段43规范为KNOWLEDGE，用户无需选择“是否核验”。历史AGENT回答不等同于已核验结果。
- 统一入口可以由服务端工作流实现，不要求顶层自由 Agent，也不要求改框架或增加多 Agent。
- 如保留上层编排，可信服务的回答、状态及引用作为独立结果交付。重新综合事实需要再次核验，不能降级为未经核验的自由回答。
- 澄清、范围绑定、取消、SSE、历史记录和调用成本都纳入兼容验证；不会仅修改模式名称就宣布完成收敛。

## 每轮协作和验收方式

每次先说明业务问题、方案及关键取舍，再实现一小段可验证的闭环。完成后记录改动、测试、真实运行结果、限制与 Git 提交；遇到范围变化先更新本路线的相关条目。

评测标签、自动检查与人工语义结论分别说明。保留失败记录，不通过重跑挑高分或放宽门槛来宣布改进。现有练习库只用于稳定练习，故障及撤回测试使用独立测试资料。

## 暂不纳入必做范围

- 新客服工单功能，以及把旧工单简单改名为知识反馈。
- 知识反馈与维护者处理闭环：有明确需求后再做，优先级低于 B/C/D。
- 多租户、复杂部门 ACL、长期记忆、多 Agent、框架迁移。
- 多种外部连接器、段落级增量向量化、全库冲突扫描。
- 为面试专门建设展示页面或部署展示站点。
- 对同一小题集持续调提示，直至偶然获得更好成绩。

完成 A—E 后进入使用与面试准备；新的功能只有在明确业务需求或验证暴露的必要缺口下再立项。
