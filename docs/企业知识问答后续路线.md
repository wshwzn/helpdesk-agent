本文是当前后续开发顺序，承接《企业知识可信问答开发目标》，结合阶段 31 后的讨论收敛范围。各阶段状态以下方进度为准，未完成的内容仍为规划，不要求一次完成。

## 项目定位与完成边界

面向单个企业内部的知识助手：知识维护者管理资料及版本，员工查询制度和操作流程；助手根据证据回答，必要时澄清条件或补充检索。主线为“资料持续更新 → 按需检索证据 → 核验后回答”。

客服工单退出产品主线。Agent 能力体现为根据已有证据决定下一步检索，而不是保留创建、查询工单工具。技术上继续复用 Spring AI、现有后端和可信问答链路。用户的面试主要是口头交流，页面展示不是交付门槛。

本次确定的必做范围止于：定位收敛、文档级增量更新、受控多跳检索、统一可信问答入口，以及相应评测与口述材料。不因发现一个新失败就自动扩大功能范围。

- 已有内部文档提交的持久化索引任务、有限重试和执行批次隔离，也已支持上传候选新版、重复识别、审核交接和取消未来安排。已接入单个配置 Bucket 下的 OSS 目录来源、手动/定时扫描和新增/修改/未变/缺失识别，变化进入原有任务及审核。内部文件上传中断恢复、外部快照孤儿清理仍有限制。KNOWLEDGE 仍是单轮检索。

## 实施顺序

| 阶段 | 要解决的问题 | 主要交付 | 验收边界 |
| --- | --- | --- | --- |
| A. 定位与工具边界收敛 | 客服背景与企业知识问答不一致 | 盘点入口、提示词、工具注册及文档；主线退出工单工具；明确员工问答和管理员维护的职责 | 主问答流程不再引导查工单或建工单；旧模式明确兼容定位，不冒充已核验知识回答 |
| B. 文档级增量更新 | 内部文档尚无完整更新流程，来源同步与失败恢复也不完整 | 提交后可靠索引、上传新版、候选版本与审核替代，再接一种外部来源及变更识别 | 提交不丢任务；仅处理受影响文档；失败保留旧可用版本；未审核不生效；重复及中断不造成错误切换 |
| C. 受控多跳检索 | 下一次查询依赖上一轮证据时，单轮检索能力不足 | 搜索与读取来源上下文、累计证据、缺口判断、预算和停止条件、逐轮诊断 | 必须跨步骤寻找证据的问题可验证；中间关系可追溯；缺证据或预算耗尽时停止；不会绕过准入及最终核验 |
| D. 统一可信问答入口 | 用户切换模式会改变知识回答的核验保证 | 简单与复杂问题复用同一服务；接入澄清与续答；迁移旧模式入口及结果展示契约 | 对外主入口不因模式不同绕过核验；不把可信结果自由改写后仍标为已核验；历史消息可读 |
| E. 项目收尾 | 功能与简历说法、验证证据不一致 | 全链路回归、成本和失败分析、架构说明、简历描述、口头追问 | 新增能力均有实际验证；数据标明样本和口径；用户能解释关键流程与限制 |

A、B 已完成当前约定范围，保留历史表及兼容模式，下一步进入 C。D 是入口与兼容收敛，不再另造一套问答引擎。测试、诊断和说明随各阶段交付，E 仅做汇总验收，不把测试推迟到最后。

## B 阶段拆分：增量更新

1. **内部文档提交与可靠索引（B1）**：上传后先配置元数据，使用“保存并提交”一次请求完成元数据保存与任务入库；后台自动执行，管理员仍单独发布。保留仅保存和手动索引接口，不扫描所有 PENDING 文档。持久任务支持有限重试、租约恢复和执行批次隔离；任务领取扫描不是来源变更识别。
2. **上传新版与审核替代（B2）**：针对已有文档上传新版，明确新旧关系并比较文件内容及业务元数据；变化文档整体重新解析、分块和向量化，复用 B1。原始文件和候选版本独立保存，失败不影响旧可用版本。准备成功后由管理员审核切换；未来生效资料不能提前撤回旧资料。
3. **来源接入与定时变更识别（B3）**：以明确配置的 OSS 外部来源为优先方向，不再默认本地目录。区分知识库托管文件和外部来源，逐份明确维护入口；仅扫描纳入同步管理的来源。首次发现、修改、未变、缺失各有规则。完整扫描才能判定缺失，撤回策略显式约定，不将外部删除自动等同于业务失效。沿用 B1/B2 的任务、候选和发布机制。

内部上传或上传新版经过本系统接口，变更已知，直接创建任务，无需再扫描 OSS 才发现。外部来源才需要轮询或事件通知来发现变化；内容变化与索引是否完成是两个维度。单纯上传和仅保存元数据的待处理文档不被定时调度擅自接管。当前不做双向回写或两边同时编辑同一份资料。

区分三个概念：来源内容发生变化、业务制度版本变化、技术索引构建批次。不能把它们都塞进一个“版本号”，也不能按文件修改时间决定制度生效。未来生效资料不得导致旧资料提前撤回。

第一版采用文档级增量，不做段落级 Embedding 复用或全库索引切换。字段、表结构、锁与恢复协议在每个实现步骤开始前给出具体设计；此前讨论的表名和流程只是设计方向。涉及数据库时新增 Flyway 迁移并同步数据库字典。

## C 阶段拆分：多跳问答

1. **C1 已完成**：冻结 `enterprise-multihop-v1` 的依赖关系样本与单轮基线，覆盖直接、两跳/三跳、并列、同义、缺规则、冲突、循环及部分可答。单轮能直接答出的短链如实保留，漏冲突的错误确定回答也完整保留。详见 `evaluation/runs/2026-10-20-多跳单轮基线.md`。
2. **下一步 C2**：扩展受控检索循环，模型提出补查需求，服务端校验查询并执行。首版拟最多 3 轮（含首轮），两次补查各最多 2 个查询，总搜索上限 5、规划模型最多 2 次；总证据量、字符及耗时预算在实现前明确。内部可查的制度映射先补查，不能直接转成对用户的追问；需检查并列需求和具体等级资料，降低漏冲突风险。预算按同题对照确认，不声称所有问题都需要 3 轮。
3. 对累计证据去重，保留来源及中间关系；范围与知识库在本次运行内绑定。读取上下文只能访问获准来源，不能接受任意文件路径。
4. 明确证据充分、无新增证据、查询重复、预算耗尽等停止原因；缺关键依据返回恰当业务状态，调用故障仍为技术失败。
5. 将多问题覆盖与部分回答纳入这一阶段，明确已回答和未知部分，不再单独开一轮无边界的复核提示调优。

多跳过程不会替代最终引用校验、语义复核和资格复查。引用可追溯不等于模型推理必然正确；需与单轮基线同时比较完成情况、错误放行、技术失败和成本。不能只展示成功的复杂题。

## A/D 阶段的兼容原则

- 退出客服工具先从注册和提示词做起，旧模块和数据不立即删除；任何破坏性清理另列具体迁移方案。
- 主问答使用可信服务；旧 AGENT 在迁移期间只能被描述为旧路径，不能宣称两个模式已经等价。最终用户无需选择“是否核验”。
- 统一入口可以由服务端工作流实现，不要求顶层自由 Agent，也不要求改框架或增加多 Agent。
- 如保留上层编排，可信服务的回答、状态及引用作为独立结果交付。重新综合事实需要再次核验，不能降级为未经核验的自由回答。
- 澄清、范围绑定、取消、SSE、历史记录和调用成本都纳入兼容验证；不会仅修改模式名称就宣布完成收敛。

## 每轮协作和验收方式

每次先说明业务问题、方案及关键取舍，再实现一小段可验证的闭环。完成后记录改动、测试、真实运行结果、限制与 Git 提交；遇到范围变化先更新本路线的相关条目。

评测标签、自动检查与人工语义结论分别说明。保留失败记录，不通过重跑挑高分或放宽门槛来宣布改进。现有练习库只用于稳定练习，故障及撤回测试使用独立测试资料。

## 暂不纳入必做范围

- 新客服工单功能，以及把旧工单简单改名为知识反馈。
- 知识反馈与维护者处理闭环：有明确需求后再做，优先级低于 B/C/D。
- 多租户、复杂部门 ACL、长期记忆、多 Agent、框架迁移。
- 多种外部连接器、段落级增量向量化、全库冲突扫描。
- 为面试专门建设展示页面或部署展示站点。
- 对同一小题集持续调提示，直至偶然获得更好成绩。

完成 A—E 后进入使用与面试准备；新的功能只有在明确业务需求或验证暴露的必要缺口下再立项。
