# 证据约束回答与核验

## 设计与业务规则

第一阶段解决“哪些文档可以进入检索”，本阶段解决“哪些模型结论可以发给用户”。在现有会话 API 内增加显式 KNOWLEDGE 模式，复用检索和消息生命周期。默认 AGENT 仍为原自动工具流程；只有显式模式具有以下强制约束，不把普通 Agent 的提示词约定当作程序保证。

```text
保存 USER 和 PENDING ASSISTANT（短事务）
    → 当前问题 + 显式范围检索默认库
    → 服务端分配 E1/E2，并保存文档 ID、Chunk、元数据与原文快照
    → 模型生成结构化草案（不带历史和工具）
    → 程序检查状态结构、引用编号、逐字出处、冲突双方文档
    → 第二次模型调用结合全部候选复核语义
    → MySQL 再查证据是否已撤回、到期或元数据变化
    → 固定模板生成正文，正文与报告一起提交（短事务）
```

- 问题最多 2000 字；范围为大写代码，省略取 ALL，只查通用资料。调用方传 CN_SH 才使用上海资料，不从自然语言或历史上下文猜范围。每轮须提供完整问题。
- 四种回答状态：可回答、需补条件、证据不足、疑似冲突。部分事实有据时允许保留；冲突双方至少两份实际文档，暂不裁决。优先级为冲突、缺条件、证据不足、可回答。
- 每项事实结论引用真实的本轮编号和连续原文，引用长度 4～1500 字，最多 5 项；结论最多 8 项、每项 1000 字，问题最多 5 个，冲突最多 3 项。引用标签由服务端生成，不接受模型自写标签。
- 草案与复核是同一模型的两次独立调用。复核看到全部本轮候选，需检查遗漏冲突、条件/否定/金额曲解以及无故拒答。程序只保证结构和出处；语义正确性仍依赖模型，不承诺零幻觉。
- 没有默认库或没有命中时无需调用回答模型，分别记录 NOT_CONFIGURED 和 NO_MATCH。检索故障、非法 JSON、伪造出处、复核否决、生成期间证据变化都标为 FAILED，而不是业务上的“证据不足”。
- 候选最多 50 个、正文合计最多 50000 字；模型单次输入 JSON 最多 100000 字，输出最多 32000 字。超限失败，不静默截断；生产参数应按模型上下文预算配置。
- SSE 知识模式只在核验及保存后发一次完整 delta；未审核草案永不提前推送。取消与完成落库共用临界区，防止取消后迟到结果落为完成。
- `knowledgeAnswer` 保存全体候选，兼容 `citations` 只显示实际引用。历史查询直接读取当时报告；撤回和过期不修改旧回答。Token 合计两次回答调用，缺失用量保留 NULL；不含 Embedding 成本。

## 新增类和文件

- `ChatMode`：区分普通自动工具与受约束知识模式。
- `KnowledgeAnswerDraft`：状态、带引用的事实结论、补充条件、冲突双方的结构化协议。
- `KnowledgeAnswerReport`：报告版本、原因、范围、知识库、核验时间及全部证据快照；计算实际引用列表。
- `KnowledgeAnswerGuard`：确定性校验状态关系、列表上限、证据编号、逐字引文、冲突双方文档身份。
- `KnowledgeAnswerModelClient`：无工具的草案/复核提示、严格 JSON 解析及调用用量。
- `TrustedKnowledgeAnswerService`：检索、核验、准入复查、模板渲染的编排，不持有数据库长事务。
- `KnowledgeAnswerReportTypeHandler`：JSON 文本与报告的数据库转换，支持业务时间往返。
- `V17__add_knowledge_answer_report.sql`：消息模式、范围、报告字段和模式检查约束。
- `TrustedKnowledgeAnswerServiceTest`、`KnowledgeAnswerModelClientTest`、`TrustedKnowledgeConversationIntegrationTest`：分别验证知识编排与引用边界、模型协议、HTTP/SSE 与真实 H2 持久化。
- `docs/demo/trusted-knowledge/conflict/`：单独导入的虚构冲突资料，避免污染正常问答场景。

## 修改类和文件

- `SendMessageRequest`：模式及范围参数、兼容构造和跨字段校验。
- `ChatMessage`、`ChatMessageResponse`、`ChatCompletionResult`：保存与返回核验报告、模式和范围，普通完成结果保持旧构造方式。
- `ConversationPersistenceService`：保存输入快照，完成事务同时写正文和报告，历史消息回读报告。
- `ConversationServiceImpl`：同步/流式分流、知识失败码、核验后 SSE 输出与取消处理。
- `ConversationController`：OpenAPI 描述区分两种输出策略。
- README、数据库字典、演示资料说明：同步接口协议、数据字段与验证边界。

## API 与数据库变化

- 原 `POST /api/conversations/{id}/messages` 及 `/messages/stream` 增加 `mode`、`applicabilityScope`；默认仍兼容旧客户端。知识模式无需模型流式能力。
- 消息响应及历史响应增加 `mode`、`applicabilityScope`、`knowledgeAnswer`；引用数组仅在知识模式改为真正被结论使用的来源。
- V17 新增 `mode VARCHAR(20) NOT NULL DEFAULT 'AGENT'`、`applicability_scope VARCHAR(40) NULL`、`knowledge_answer MEDIUMTEXT NULL`，新增 `ck_chat_message_mode`。无新增索引；JSON 内部和字段间业务规则由应用保证，详见数据库字典。
- 同步失败返回 502 CHAT_GENERATION_FAILED；SSE 开始后的失败返回 error；内部消息错误码为 KNOWLEDGE_ANSWER_FAILED。失败不保存草案。旧自动工具记录与待确认工单接口保持兼容。

## 已知限制与后续

- 未实现全库冲突发现。两个矛盾来源只有都进入本轮检索候选才有机会被识别；复核模型也可能误判。未来用固定问题集测漏检和误报，不以 mock 测试代替真实评测。
- 当前核验失败直接终止，没有自动修复循环。默认模型还必须配置，即使最终没有证据而无需回答模型调用。
- 最后一次准入复查与用户收到回答之间仍有时间窗口，不承诺跨生成过程的数据库一致性快照。新资料在检索之后发布也不会自动加入当前候选。
- JSON 证据随消息重复保存，增加存储和历史接口体积；后续可按需求拆分审计详情接口或证据表。
- 当前模式由 API 显式选择，未增加前端选择器、范围目录或自然语言条件抽取；跨轮指代与补充条件需用户重述完整问题。
- 尚未实现文档自动增量更新、索引原子切换和真实模型专项评测。后续先跑固定正常、缺条件、无依据、冲突案例，再决定迭代修复策略。
