# 可信问答脚本评测与失败诊断

## 实现行为与业务规则

- 先用真实模型、真实 MySQL 和 ES 调用原有 HTTP 接口，再根据运行结果修复，不预填准确率。
- 固定 15 道开发回归题；正常、冲突、撤回恢复、撤回后无依据按顺序分别运行。完整模式创建独立知识库，沿用原检索参数；保留用户的原文档和发布状态，结束恢复原默认库。
- 每题独立对话，单次请求不自动重试。技术失败保留在已执行题数内，独立统计，不当作正确拒答；旧输出目录禁止覆盖。
- 运行前核对固定资料的 SHA-256、业务身份、有效期和发布状态，运行期间检查默认库/模型配置变化，防止把错误环境测成问答问题。资料日期超过固定有效窗口时需更新题集，不能悄悄修改系统时间。
- 报告记录题集、源码及资料摘要、调用模型、检索设置、文档状态、实际证据、答案、耗时和可获得的 Token。自动检查只保证结构、预期状态和出处等，不保证语义正确；真实语义判断另行标注审阅者类型。
- 首轮暴露了泛化错误码无法定位问题，因此增加固定阶段异常，不暴露厂商异常或草案。同步/SSE 都把阶段码保存到消息历史，外层脱敏错误协议保持兼容。
- 试验过收紧提示：区分缺地区/缺资料、减少无关流程、避免把范围重叠说成范围相同等。两次完整试验没有取得更好的自动通过结果，且定向诊断确认复核误杀；仅保留原因枚举提示的第三次实验也表现更差。因此最终代码的 RULES、DRAFT_PROMPT、REVIEW_PROMPT 全部恢复到原提交的原文，只保留代码层的阶段分类。解析器兼容可选原因枚举，但默认提示不要求模型输出原因，通常记录 KNOWLEDGE_REVIEW_REJECTED。
- 本轮没有自动修复/重试循环，也没有降低引用校验标准或把失败回答改成正常拒答。

## 新增文件与职责

- `scripts/evaluate_trusted_knowledge.py`：标准库 HTTP 客户端、凭据读取、场景准备、顺序运行、确定性检查、逐题报告及默认库恢复。
- `scripts/test_evaluate_trusted_knowledge.py`：评测工具的反例测试，防止错误状态、假引文、错误 Chunk 和技术故障被计为通过。
- `docs/evaluation/trusted-knowledge-cases.json`：固定题集、预期状态、必要来源及辅助关键点。
- `docs/evaluation/README.md`：运行方式、分母、判分边界、用量限制、恢复方法和错误码说明。
- `KnowledgeAnswerFailure`：允许安全持久化的失败阶段枚举。
- `docs/evaluation/runs/`：脱敏后的逐题真实数据、候选原文、运行配置、定向模型交互及对照分析。

## 修改文件与职责

- `KnowledgeAnswerGuard`：区分结构错误和引用身份/逐字出处错误，校验强度保持不变。
- `KnowledgeAnswerModelClient`：保留原布尔复核提示，解析器兼容可选固定原因枚举，明确协议和上下文超限异常。原因提示实验未采用；若模型提供原因，该原因仍只是模型判断。
- `TrustedKnowledgeAnswerService`：在检索、草案、复核、准入复查边界捕获外部故障并转换成固定阶段码；精确异常不被覆盖。
- `ConversationServiceImpl`：同步与 SSE 持久化相同的安全阶段码，未知异常仍兼容通用码。
- 三个 Java 测试类：覆盖阶段分类、精确协议异常保留、原始异常不泄露及同步/SSE 错误落库。
- `.gitignore`：忽略 Python 编译缓存；报告原始文件及临时令牌放 `target/`，不提交凭据。
- README、数据库字典和演示说明：链接评测入口并更新错误码语义，无数据库结构变化。

## API 与数据库变化

- 无新增业务 API、表、列或 Flyway 迁移。已有 `chat_messages.error_code VARCHAR(50)` 容纳全部新分类码。
- 失败的知识消息仍无正文、无核验报告。同步 HTTP 502 和 SSE error 仍使用 CHAT_GENERATION_FAILED；客户端可通过历史消息查看阶段。
- 评测脚本调用注册以外的既有接口：正常登录、文档上传/元数据/索引/发布/撤回、默认库、会话及消息；不会直接访问数据库绕过权限。

## 测试与真实验证

- 改造期间 Java 全量 122 个测试通过，0 失败/错误/跳过；后续增加原因解析测试并回退提示后，最终代码执行 35 个相关测试及打包通过。Python 判分与默认库恢复测试 11 个通过。
- 原服务冒烟曾失败一次（HTTP 502、通用码），后续现有冲突库两题通过；失败记录保留，不推断其原因。
- 首轮独立库 15 题：13 题通过自动检查，1 题技术失败，1 题缺条件未追问。默认库恢复成功。对照原文又发现冲突总结与引用覆盖不足，证明状态通过不等于语义通过。
- 第一轮提示实验 12/15 自动通过：两题被复核否决，一题在范围已明确时仍追问。第二轮提示实验 11/15 自动通过：4 题技术失败。第三轮只保留原因枚举提示的实验为 8/15，6 题被复核拒绝、1 题状态不符。所有失败保留，不因为成绩降低而换题或删题。
- 7 题定向诊断使用已有的临时协议日志。发现 B04/B05 草案与引文正确表达当前每晚 600 元、超出不报销，复核仍标为 UNSUPPORTED_CLAIM；W01 不该要求用户挑选制度版本，复核则正确阻断。可见复核同时存在有效拦截和误杀。
- 最终三个提示常量均与原提交逐字一致，真实完整回归 12/15 自动通过：B06 复核否决、C02 引用校验失败、B08 状态不符。13 个成功报告有 16 处引用且逐字检查通过；助手审阅又指出 C01 的结论到引文覆盖不足，不能把 12/15 称为语义准确率。完整对照见 `docs/evaluation/runs/2026-10-19-可信问答实测报告.md`。
- 七轮结构化运行均导出脱敏逐题数据（含失败实验和定向交互）；另记录一次早期冒烟失败。原默认库 7、文档 145～151 全部元数据、检索配置及默认模型通过 API 复核未变；专用评测库 8～13 保留审计。临时 8081 服务停止、身份文件删除，原 8080 服务健康。新的阶段码需要重启原后端后使用。

## 已知限制与后续工作

- 题集规模小且用于调整提示，不是独立盲测集；单次前后差异含模型随机性，不能证明统计显著改进。
- 无全库冲突扫描，检索漏召回的来源不会进入判断；语义复核仍可能错判。开发助手审阅不等于独立人类金标准。
- 失败调用尚未持久化完整证据链和 Token，阶段码提供定位但不包含厂商原文；报告的已知用量不是完整成本。
- 默认库是全局配置。脚本临时切换期间不适合同时服务其他知识对话；进程强杀可能无法恢复，需按报告操作恢复。
- 本轮推进的是可重复评测、诊断缺失修复和可观测性，尚未实现自动增量更新/索引原子切换，也未改动前端工程。
