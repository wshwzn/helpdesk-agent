# 问答运行记录与失败诊断

## 设计与业务规则

本轮解决“知道失败码，却看不到失败时证据和草案”的问题。客户消息仍只展示通过核验的正文；诊断单独保存，管理员按运行 ID 复查。复核提示和问答判断标准保持原样，不把模型原因当成人工结论。

1. 会话归属、请求和模型配置校验通过后，在创建助手消息的原事务中分配 UUID；成功和失败的知识消息都保留 `knowledgeRunId`。AGENT、客户消息及旧数据为空。
2. 保存运行初始记录和每个阶段的开始、结束快照：检索 → 草案 → 结构/引用校验 → 语义复核 → 证据准入复查 → 最终消息保存。只有消息保存成功后才把运行标为 SUCCEEDED。
3. 检索后记录实际候选、排名、参数和本轮证据编号；草案解析后立即保留，在校验失败时也可复查；复核结论先保存到上下文再判定是否放行。
4. 每次快照通过独立短事务落库；诊断写入异常仅输出运行编号和异常类型，不改变业务成功或原始异常。后续阶段尝试写入累计快照并保存此前写入失败次数。
5. 诊断上下文显式传递，不使用 ThreadLocal。取消是终态，迟到模型返回不能追加草案、继续复核或覆盖终态；数据库同时以状态和递增修订号防止迟到更新。
6. 模型用量按阶段记录，未知保持 NULL。即使响应无法解析，只要厂商已返回 Token 仍保留；不保存畸形原始响应、请求头、密钥或厂商异常正文。

诊断快照与最终消息是两个独立写入，无法同时保证“诊断永不影响业务”和“每次业务都有完整诊断”。本实现选择业务优先：写入失败可导致缺失/未结束记录，管理员接口与评测明确呈现这种情况。

## 新增文件与职责

- `V18__add_knowledge_answer_runs.sql`：消息运行编号、诊断表、唯一约束和筛选索引。
- `KnowledgeAnswerRunSnapshot`：版本化管理员快照，定义运行/阶段状态、证据与逐阶段用量。
- `KnowledgeAnswerTrace`：每请求的阶段计时、草案/复核捕获、取消终态及故障隔离。
- `KnowledgeAnswerRunStore`：JdbcTemplate 参数化 SQL、独立短事务、修订号条件更新及分页摘要查询。
- `KnowledgeAnswerRunService`：把已接受消息与模型身份关联到诊断上下文。
- `AdminKnowledgeAnswerRunController`：管理员运行摘要和完整诊断接口。
- `KnowledgeAnswerRunIntegrationTest`：真实消息/诊断数据库和核验编排，替换外部检索与模型后测试权限、失败、取消及写入故障。

## 修改文件与职责

- `ChatMessage`、`ChatMessageResponse`、`PreparedChatExchange`、`ConversationPersistenceService`：生成、传递和返回运行 UUID；不把草案放进客户 DTO。
- `ConversationServiceImpl`：同步和 SSE 启动诊断，记录最终消息保存结果，取消后保持终态。
- `TrustedKnowledgeAnswerService`：原有判断逐阶段执行并采集快照；保留直接业务调用重载，正式会话入口显式传入诊断。
- `KnowledgeAnswerModelClient`、`KnowledgeAnswerFailure`：在协议解析前获取已知 Token，失败时以安全对象传递用量；提示常量不变。
- `TrustedKnowledgeConversationIntegrationTest`：适配显式上下文调用，并清理本测试诊断数据。
- `KnowledgeAnswerModelClientTest`：畸形响应有已知用量时仍保留，且不泄露正文。
- `OpenApiDocumentationIntegrationTest`：检查管理员诊断详情与列表在 Swagger 中声明 Bearer 授权。
- `evaluate_trusted_knowledge.py`：从成功/失败消息关联管理员诊断，核对运行、消息、会话、问题与范围；诊断成绩和问答成绩分别统计。
- `test_evaluate_trusted_knowledge.py`：验证诊断不可用/身份不符/未结束不会覆盖问答结果，已知失败用量与未知部分分别计数。
- README、评测说明、数据库字典：同步接口、运行方式和状态语义。

## API 与数据库

- 消息响应新增可空 `knowledgeRunId`，成功响应和消息历史均可读取。SSE 失败后通过已有 `assistantMessageId` 查询消息历史获得运行编号；草案不会作为 delta 或错误正文发送。
- `GET /api/admin/knowledge-answer-runs?page=1&size=20&conversationId=...&status=FAILED`：摘要分页，页大小最大 50，筛选项可选。
- `GET /api/admin/knowledge-answer-runs/{runId}`：完整诊断；缺失返回 404 `KNOWLEDGE_RUN_NOT_FOUND`，不补造记录。匿名 401、客户/客服 403，沿用现有 `/api/admin/**` 授权规则。
- V18 只追加表与列，升级前知识消息的运行 ID 保持 NULL。字段、默认值、索引、枚举、逻辑关系和应用约束详见 `docs/database-schema.md`。
- `--require-diagnostics` 在诊断缺失、身份不匹配或消息已终结但诊断未终结时返回非零退出码；实际问答 outcome 保持原样。已有旧服务仍可跑评测，只是诊断标为 NO_RUN_ID。

## 已知限制与下一步

- 新增诊断不等于提高回答准确率；复核误杀、缺地区未追问、结论到引文覆盖不足仍需要独立设计和评测。
- 已接受消息之前的认证、请求校验和默认模型解析错误没有运行记录；进程中断或最终写入失败可能留下 RUNNING，需结合消息状态判断，未实现诊断补偿。
- 独立诊断写入增加数据库访问和延迟；事务有超时，但连接池等待仍受基础设施配置影响，不保证数据库故障时零额外等待。
- 当前保留诊断用于开发审阅，无自动清理任务。快照含客户问题及知识正文，只开放管理员权限；后续部署前按实际数据治理需求确定保留期。
- 未调用的阶段没有用量，协议失败只能保存已知用量和固定码，无法解析的原始文本不保留。Embedding、厂商未返回和取消后迟到的用量仍可能未知。
- 初始记录写入失败可在后续恢复；所有写入均失败时，消息运行 ID 仍存在但管理员查询为 404。评测不会把这种情况算成完整诊断。
