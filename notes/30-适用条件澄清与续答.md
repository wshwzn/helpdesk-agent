# 30-适用条件澄清与续答

## 为什么这样设计

历史 B08 的 `ALL` 仅能召回通用报销流程，模型无法从这些证据判断地区制度是否存在，曾出现直接判证据不足或被复核否决。先按原样冻结阶段 28 的 B08、阶段 29 的 B06/B08（含来源文件 SHA、原问题、证据、草案、诊断），不把重写的样本冒充历史重放。冻结数据在 `docs/evaluation/clarification-historical-failures.json`，仍非独立人工金标准。

新增“适用条件配置 → 主题识别 → 服务端追问 → 显式选择 → 原问题重新检索”的闭环。配置定义业务主题，不提供金额等事实答案；模型只返回主题 ID，程序确定必要条件。普通报销流程和住宿金额可配置成不同主题，避免所有问题一律问地区。

## 已实现行为与规则

- 管理员按知识库设置主题、业务描述、范围选项；空选项表示该主题不要求范围，空主题列表关闭路由。旧库升级默认为关闭。
- 仅 `KNOWLEDGE + ALL + 非空配置` 调用主题路由。显式指定范围直接走原检索；不从正文猜地区，不跨范围检索制度。
- 模型返回的主题必须来自配置且不能重复；不确定或多个主题没有共同可选范围时技术失败。多主题需要范围时取选项交集。
- 缺范围时返回 `APPLICABILITY_REQUIRED / NEEDS_CLARIFICATION`，只包含问题和选择项，没有事实结论、引用或制度证据。此时没有 DRAFT、REVIEW、ES 检索调用。
- 续答需要 `clarificationMessageId` 和显式 `applicabilityScope`。服务端先校验会话归属及活动状态，再要求来源是本会话最新、已完成、可续答的知识澄清助手消息。
- 原问题、原知识库与配置修订来自已落库报告，不能由客户端覆盖。选项必须存在；默认知识库切换不改变续答所绑定的原库。配置变更则拒绝旧卡片。
- 续答不复用旧证据，按新的范围和当前时刻重新检索、选择原文段落、独立复核、检查文档资格。文档已撤回/到期仍按现有过滤处理；配置在生成中改变也不能交付旧判断。
- 同步与 SSE 共用有效输入；SSE 仍仅在核验和落库之后发送正文。沿用会话乐观锁和生成中状态避免并发覆盖，历史澄清快照保持不变。
- 用户补充消息正文按原话留存，但有效问题来自原始澄清；修改问题应另发普通知识请求，不带澄清 ID。来源一旦不是最新消息即不能续答，包括续答失败后重试，此时重新发送原问题。
- 新问题不会自动继承上次地区。旧模型自然语言 `NEEDS_CLARIFICATION` 没有结构化卡片时仍保持原行为，不能使用新续答参数。

## 新增文件职责

- `KnowledgeApplicabilityPolicy`：配置 DTO、主题/选项、模型路由及诊断快照结构。
- `KnowledgeApplicabilityService`：配置读写、Bean Validation 和业务校验、乐观并发、主题检查、选项交集、修订复查。
- `KnowledgeAnswerInput`：服务端恢复的原问题、范围、知识库与续答关联。
- `KnowledgeClarificationException`：区分非法参数 400 与过期上下文/并发修改 409。
- `V19__add_knowledge_clarification_policy.sql`：知识库配置 JSON 及独立修订号。
- `KnowledgeClarificationIntegrationTest`：真实 H2、鉴权、HTTP、会话持久化与澄清编排；仅检索/模型使用替身。
- `KnowledgeApplicabilityServiceTest`：路由协议、主题校验、多主题范围交集及输入边界。
- `scripts/evaluate_knowledge_clarification.py` 与对应测试：隔离资料库的固定 15 题、上海/北京两轮续答以及拒绝非法续答验证；不自动重跑失败模型调用。
- `docs/demo/trusted-knowledge/clarification-policy.json`：可公开演示的业务配置；没有嵌入 Java 判断或以用例编号路由。

## 修改文件职责

- `KnowledgeBase`、`AdminKnowledgeBaseController`：新增配置字段和管理接口；既有库详情格式保留，配置由独立接口读取。
- `SendMessageRequest`、`PreparedChatExchange`、`ConversationPersistenceService`、`ConversationServiceImpl`：接收澄清消息 ID，在短事务内恢复原问题，统一同步/SSE 调用。
- `KnowledgeAnswerModelClient`：增加独立的主题分类调用；原草案、BASELINE/CHECKLIST 复核提示均保持原文，默认 BASELINE 不变。
- `TrustedKnowledgeAnswerService`：先判断条件，或按原问题续答；范围/条件不改变原文引用和独立复核要求。
- `KnowledgeAnswerReport`：可空的 `clarification` 和 `continuationOfMessageId`；旧报告可回读，带新结构的报告 schemaVersion 为 2。
- `KnowledgeAnswerTrace`、`KnowledgeAnswerRunSnapshot`、`KnowledgeAnswerRunService`：增加 APPLICABILITY 阶段与配置/路由/续答来源；诊断问题为实际用于检索的原问题。诊断 JSON schemaVersion 仍为 2，新增可空字段兼容历史。
- `KnowledgeAnswerFailure`、`GlobalExceptionHandler`：新增条件调用失败、不确定、配置变化码及前置业务错误响应。
- 既有评测脚本：诊断总用量新增实际尝试的路由调用；成功消息 Token 同样包含路由，二者重叠不能相加，仍不含 Embedding。
- 既有构造测试与诊断测试：适配新增依赖；显式范围路径仍验证原六阶段。
- 数据库字典、演示文档、评测说明和 README：补充配置、接口、成本及限制。

## API 与数据库

- `GET /api/admin/knowledge-bases/{id}/clarification-policy`：ADMIN 读取配置，未配置返回 revision=0、topics=[]。
- `PUT /api/admin/knowledge-bases/{id}/clarification-policy`：ADMIN 整体替换，提交当前 revision，成功加一。应用校验主题唯一、范围不可为 ALL、同码名称一致和长度上限。
- `POST /api/conversations/{id}/messages` 及 `/messages/stream` 增加可选 `clarificationMessageId`；仅知识模式且明确范围可使用。400 参数非法，409 旧卡片/配置冲突；其他会话归属仍按原规则返回 404。
- V19 添加 `knowledge_bases.clarification_policy MEDIUMTEXT NULL`、`clarification_revision BIGINT NOT NULL DEFAULT 0`；同时使用既有 `version` 乐观锁，不新增表或外键/索引。字典同步到 `docs/database-schema.md`。
- 澄清状态保存在已有消息报告中，不另建会话长期记忆或待办表。通过“最新消息 + 报告状态 + 会话乐观锁”限制续答；原问题不拼接到用户正文中。

- B03、B09 被 BASELINE 复核否决，完整草案/诊断保留；既有复核问题没有通过本轮改动掩盖。18/18 诊断齐全、返回 23 引用均通过身份/连续原文检查，诊断已知总 Token 34933（含路由 1390，不含 Embedding）。

- 真实读取旧诊断 schemaVersion 1/2 成功；新增 applicability 为 null。主源码摘要与实测 JAR 对应，实测后仅补充测试和文档。临时 8081 服务已停止，本地测试令牌文件已删除，原 8080 服务健康检查仍为 UP。

## 已知限制与后续

- 本轮只支持显式选择一个适用范围，不支持自然语言自动填槽、多轮逐步补多个条件、部门/员工类别等复合维度。
- 主题匹配仍由模型判断，可能漏匹配或误匹配；这不是确定性意图识别，也不能声称解决全部澄清错误。管理员应维护主题描述及范围码，与文档元数据保持一致。
- 配置不是证据。选择地区后仍可能没有有效文档、发现冲突或被复核拒绝。既有复核误杀问题仍需独立评测。
- 无 Web 页面改动，本轮先交付接口/脚本；可据报告的 scopeOptions 渲染选择卡片。
- 不建设配置变更历史表；历史消息和诊断保存各自快照。配置修订变化会让未完成旧卡片失效；需要用户重新提问。
