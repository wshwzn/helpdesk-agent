# 规则核查与回答状态衔接

## 行为与规则

候选实现与真实对照已完成，但整体退化，未默认启用。`app.knowledge.multihop.rule-checks-enabled` 默认 false，显式 true 才启用下述规则协议与回答上下文；关闭时复用阶段 37 的原规划提示、校验和草案行为。规划声明具体规则的原文锚点和查询；服务端核对原文、查询含规则词，并以实际搜索记录解除核查责任。未完成核查优先于模型的 SUFFICIENT，不扩大三轮、五次搜索和两次规划预算。多轮已经声明的任务不能被后续规划遗忘。

规划区分内部资料缺口和用户条件。草案收到检索经历，但这些经历不是引用事实；未声明用户条件不得 NEEDS_CLARIFICATION，仍有规则查询未执行不得 ANSWERABLE。补查之后旧缺口判断可能过期，需要重新依据最终原文判断。

新增 REASONED 复核候选要求固定原因和缺陷位置，不批准被否决草案、不自动重写或重试草案。固定草案回放未通过准入，默认仍为 BASELINE；不以总体误放减少掩盖单轮误拒和协议失败增加。

## 文件职责

- KnowledgeMultihopProperties、application.yaml：候选开关默认关闭，支持环境变量 KNOWLEDGE_MULTIHOP_RULE_CHECKS_ENABLED。
- KnowledgeRetrievalPlan：规则核查与用户条件协议、锚点校验。
- KnowledgeEvidenceCollector：累计核查责任、调度优先级、形成回答上下文。
- KnowledgeAnswerContext：限制无依据追问和未核查后的确定回答。
- KnowledgeAnswerModelClient：规划及草案协议衔接、可定位复核候选。
- TrustedKnowledgeAnswerService、诊断快照：传递上下文并执行确定性校验，诊断版本升为 4，旧记录不补造新字段。

- KnowledgeEvidenceCollectorTest、KnowledgeAnswerContextTest、KnowledgeAnswerModelClientTest：新增核查调度、状态衔接与复核协议边界验证。
- 原服务、澄清和诊断集成测试：适配回答上下文和版本 4，同时继续验证撤回、引用及历史兼容。
- evaluate_knowledge_review.py 及测试：新增 REASONED 候选与事前诊断增强准入标准，固定回放数据不变。

## API 与数据库

无 DDL 变化。管理员诊断新增 answerContext、规划 ruleChecks/userConditions、复核 issues；客户答案契约不变。新增安全错误码 KNOWLEDGE_UNJUSTIFIED_CLARIFICATION 与 KNOWLEDGE_RULE_CHECK_INCOMPLETE。数据库字典随实现同步。

## 验证

候选初版 286 项 Java 测试、37 项 Python 测试通过；增加默认回退开关后，最终 288 项 Java 测试通过（0 失败/错误/跳过），打包成功。补充测试验证默认不调用候选、旧三字段协议可用且不注入实验提示。新增边界测试覆盖充分决策仍须核查、预算耗尽保留待查项、假规则锚点、资料缺失不能追问、真实条件可澄清、旧缺口不强制拒答，以及可定位复核拒绝缺失/伪造理由。冻结题集与资料、历史结果均不修改。

真实复核回放采用原有 24 道固定草案、BASELINE 与 REASONED 各两轮；事前准入标准为每轮误拒/误放/技术失败及挑战集均不退化，并且原因协议完整。与旧 CHECKLIST/CONTEXTUAL 的“必须降低误拒”目标不同，此次目标是增强诊断且不损害已测判定；原两策略门槛不改写。实际 BASELINE 两轮误拒/误放/技术失败为 2/3/0、1/2/0；REASONED 为 0/1/0、2/1/1。候选未准入，总体正确判定 43/48 对 40/48 不构成采用依据。

## 限制

程序只能验证已声明核查对象；模型仍可能漏声明或选错业务规则，不能保证全库冲突发现。查询执行不等于完整召回；规划缺口不是事实。预算限制及 SDK 重试口径沿用阶段 37。

真实 12 题对照：7 自动通过、1 未通过、4 技术失败，完整召回 11/12；上一轮为 9/1/2。N01 缺规则、N02 冲突改善，但 D01/H01/H02 在规划协议校验失败；H04 核查查询挤掉期限查询；N04 仍被无理由复核否决。运行与全量数据见 [对照报告](../docs/evaluation/runs/2026-10-21-规则核查与状态衔接对照.md)。原默认库 18 已恢复，冻结原文/题集未改，未重跑选优。
