# 单列表规划与候选取舍

## 实现行为与业务规则

把阶段 38–40 候选的普通查询、规则核查收敛为一份 tasks 列表。模型协议仅含 decision、gaps、tasks、userConditions；SEARCH 必须有缺口和 1–2 项任务，停止动作必须 tasks=[]。不再维护原文锚点、核查专用队列或跨轮任务账本。每批执行后才能规划下一批。

保留三轮、五次搜索、两次规划、90 秒软调度预算和查询去重。预算中断时，以实际成功搜索记录计算 pendingQueries；尚有任务未执行不能给出 ANSWERABLE。内部资料缺口与用户条件分开，无用户条件不能要求澄清。查询只用于检索，不是知识证据；适用范围、文档资格、引用解析及 BASELINE 语义复核保持原链路。

候选配置改为 app.knowledge.multihop.task-planning-enabled，环境变量 KNOWLEDGE_TASK_PLANNING_ENABLED，默认 false。旧 rule-checks-enabled 配置不再启用候选。阶段 37 默认规划保持不变。

## 运行前固定的采用标准

只运行一次原有 18 份资料、12 道题的完整对照，不改题集、不调提示后重跑选优。对比阶段 37：

- D01、D02、D03、H01、H02、H03、H04、H05、N03 九道已通过题不能退化。
- N01、N02、N04 至少改善一题；N02 不能继续错误地给出确定金额。
- 技术失败不超过原来的 2 题。
- 核对已知 Token、调用数、耗时和未知用量；成本上升时必须说明收益，不能仅凭通过数宣布采用。

收益不足则保持候选关闭，结束本项候选迭代，下一阶段转向 D 统一问答入口，不再自动调提示或添加核查规则。

## 新增与修改文件

- KnowledgeRetrievalPlan：新增嵌套 TaskPlan 承接单列表模型协议；内部 queries 保存转换后的任务，RuleCheck 仅供历史快照读取。
- KnowledgeAnswerModelClient：简化候选规划提示和协议解析；草案使用通用 pendingQueries。默认规划和复核未变。
- KnowledgeEvidenceCollector：删除核查队列、强制补查和锚点校验，仅保留最近计划与实际搜索记录。
- KnowledgeAnswerContext、KnowledgeAnswerFailure：未执行搜索阻止确定回答，新增 KNOWLEDGE_SEARCH_INCOMPLETE；旧 pendingRuleQueries 作为读取别名。
- KnowledgeMultihopProperties、application.yaml：替换候选开关名称，默认关闭。
- KnowledgeAnswerTrace：新诊断写版本 5；相关模型、采集器、上下文、集成及回放测试更新协议和版本断言。
- README、路线、评测说明、演示说明和 database-schema：同步候选取舍与诊断兼容边界。

## API 和数据库变化

无 HTTP 接口或 DDL 变更。管理员诊断 JSON 升为版本 5，answerContext.pendingRuleQueries 改写 pendingQueries；读取历史字段仍兼容。新候选计划在诊断中仍用 queries，ruleChecks=[]。旧核查字段与错误码仅保留历史读取，不表示仍执行该规则。客户消息接口不变。

## 已知限制和后续

单列表减少协议复杂度，但不能保证规划器发现所有矛盾。搜索执行过不等于证据完整；语义质量仍需用完整答案评估。90 秒仅限制新任务调度，无法硬中断 SDK 已发出的请求；Token 不包含 Embedding 或未知网络重试成本。本次决定不采用，保留关闭的候选用于审计和显式复现，不安排继续调优。下一轮转向 D 统一入口，未解决的两个失败作为项目限制继续记录。
